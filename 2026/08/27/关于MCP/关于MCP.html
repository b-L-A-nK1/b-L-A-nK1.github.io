title: 关于MCP

MCP（Model Context Protocol，模型上下文协议），旨在为LLM与其它外部工具、数据源、服务等之间建立安全统一的双向连接。MCP可以让不同的AI模型能够以一致的方式接入任意外部能力，不用为每对”模型-工具”组合单独开发适配的代码

MCP的出现使得如果有m个模型、n个工具，传统方式需要m×n次的定制代码设置开发、MCP可以将其降为m+n次，实现全互联。同时因为LLM本质上是一个文本预测引擎、MCP可以让模型执行一些操作

架构 Host-Client-Server三次模型

1、MCP Host(主机)

Host时运行LLM的宿主应用程序，例如Claude Desktop、Cursor IDE等等，其作用：

管理用户交互界面和LLM推理循环
实例化并管理一个或多个MCP Client
实施安全策略边界、决定哪些server可以被访问，哪些工具可以被调用
展示结果

2、MCO Client(客户端)

Client时Host内部的协议连接组件，和MCP Server保持一对一的逻辑连接，对于每一个Client实例都封装了：

协议状态机：管理初始化握手和能力协商
传输适配器：将JSON-RPC消息映射到具体的传输通道(stdio,HTTP等)
能力缓存：缓存server生命的tools、resources、prompts清单
生命周期管理

一个Host可以同时运行多个Client，但是每个Client只可连接一个Server，这样可以保证故障隔离、某个Server的崩溃不会影响到其他Server的可用性

3、MCP Server(服务器)

Server是提供能力的，以轻量级进程或者远程服务的形式存在，负责将特定功能(例如工具调用、资源访问、提示模板)封装并通过标准化接口暴露给Client

核心原语(Primitives)

MCP Server通过三种核心原语向Client暴露能力，行为上解释分别由执行、读取、模板三种交互模式

1、Tools，可执行的操作

控制权：模型决定，LLM自主决策是否调用
本质：可执行函数、允许模型执行操作
定义包含：name(唯一表示)、description(自然语言描述，供LLM理解)、inputSchema(JSON Schema参数约束)、outputSchema(结构化输出定义)

2、Resources，可读取的数据

控制权：应用或服务器
本质：只读数据源，例如文件、数据库记录、API响应
通过URL表示，为模型提供上下文
支持：静态资源直接读取、参数化资源模板(eg:repo://{owner}/{repo}/issues/{number})、订阅与变更通知

3、Prompts，可复用的交互模板

控制权：用户
本质：预定义的交互模板或者工作流、包含固定框架和动态变量
通常由用户显示触发、用于标准化特定任务流程

通信协议和传输层

1、消息格式：JSON-RPC 2.0

MCP所有的通信均基于JSON-RPC 2.0 协议，消息一般分为三类

Request：一方发起的操作请求，期望返回Response
Response：对Request的回复，包含结果或者错误信息
Notification：单向消息，不期望回复

例如工具调用请求:

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "query_database",
    "arguments": {
      "query": "SELECT * FROM users WHERE age > 18"
    }
  }
}

2、传输层机制

Stdio(标准输入/输出)，本地通信
通常用于本地工具调用、命令行工具
Host将Server作为子进程启动，通过stdin写入JSON-RPC消息，Server从stdin读取并处理后通过stdout返回消息，消息用换行符分隔，stderr用于日志输出
Streamable HTTP，远程通信(当前标准)
适用于远程服务、云原生部署
Server仅需单一HTTP端点，Client通过HTTP POST发送请求，Server可以在单词请求中返回标准JSON响应或者通过SSE实现流式响应，支持通过Mcp-Session-Id管理会话

SSE(Server-Sent Events)，已废弃

早期远程传输方案，但已被废弃并被Steamable HTTP替代

完整交互流程

以向Host提问某地天气如何为例

在所有流程之前会有一个前置准备阶段

Client ──── initialize 请求 ────→ Server
         (声明协议版本、客户端能力)

Client ←─── initialize 响应 ───── Server
         (返回服务端版本、能力列表)

Client ──── initialized 通知 ───→ Server
         (确认就绪，进入正常操作状态)

初始化完成之后，Client会主动查询Server提供了哪些能力

Client ──── tools/list 请求 ────→ Server
Client ←─── 工具清单响应 ──────── Server
         [{name: "get_weather",
           description: "查询指定城市的天气",
           inputSchema: {city: string}}]

Client会调用tools/list、resources/list、prompts/list等方法，获取Server当前可以使用的工具、资源和提示词列表

Server会根据Client的调用内容去返回相应内容的工具元数据

Host会将这些工具描述注入到LLM的系统提示词中，让模型知道自己有哪些工具可以用

动态更新：若Server后续新增或者移除了某些工具，会通过notifications/tools/list_changed通知Client刷新工具列表

来到阶段

用户："今天杭州天气如何？"
        │
        ▼
┌─────────────────────────────┐
│  Host 将用户问题 + 工具清单  │
│  一起发送给 LLM              │
│                              │
│  LLM 推理：                  │
│  "需要调用 get_weather 工具" │
│  参数：{city: "杭州"}        │
└─────────────────────────────┘

Host接收到用户请求后，将用户问题连同可用工具的描述信息一起传给LLM

LLM会基于上下文和可用能力列表进行推理，决定使用哪个工具

LLM生成结构化的调用指令(JSON格式)，包含工具名和参数

Client ──── tools/call 请求 ────→ Server
         {name: "get_weather",
          arguments: {city: "杭州"}}

         Server 执行实际查询操作
         （调用天气 API，获取数据）

Client ←─── 执行结果响应 ──────── Server
         {content: [{type: "text",
           text: "杭州今天晴，25°C..."}]}

Client将LLM的调用意图转换为标准的tools/call JSON-RPC请求，发送给对应的MCP Server

Server接收请求后会执行具体操作

Server将结果封装为结构化格式返回

如果执行失败，则会返回isError: true 以及错误信息，而不是抛出异常

Client 将工具返回的结构化数据
整合进 LLM 的上下文
        │
        ▼
┌─────────────────────────────┐
│  LLM 收到工具执行结果：      │
│  "杭州今天晴，25°C，湿度60%" │
│                              │
│  LLM 生成自然语言回复：      │
│  "杭州今天天气晴朗，气温25°C │
│   湿度60%，适合外出活动。"   │
└─────────────────────────────┘
        │
        ▼
    展示给用户

Client将Server返回的结构化结果整合进模型的上下文

LLM基于工具返回的数据，用自然语言回答

通过Host将回答展示给用户

高级交互机制

1、Sampling(采样)，反向请求

MCP支持双向通信：Server可以通过sampling/createMessage请求，反向让Host的LLM进行生成，实现了Server在复杂工作流中借用模型推理能力的场景，但是需要用户批准

2、Elicitation(信息请求)

允许Server在交互过程中向用户请求补充信息例如当工具参数不完整时，Server可以直接询问用户

3、Roots(根声明)

Client可以声明URI边界，界定Server可操作的资源范围，实现最小权限原则
